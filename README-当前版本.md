## ★ 2026-10-31 21:10「总是拉过头 → 过冲量 = 预算 × (k真/k估 − 1)，关掉猜出来的灵敏度系数」

指纹：`main.py` **70b82a357e97b050d0e77dc71d8ddd97**、`config.json` **3fad8c02a9c24bcef5e57fa78fde8c2b**

用户报「总是拉过头」。"总是"两个字是关键——偶发是抖动，必然就是**系统性系数错**。

**机制**：跟随线程的防过冲三层（剩余偏差／单调逼近／预算软刹车）全都在**像素域**算，而"像素 →
鼠标计数"要除掉 k（像素/计数）。k 被低估 r 倍时，发出去的计数换算成真实像素是计划的 r 倍：
过冲量 ≈ 每周期预算 × (k真/k估 − 1)，而且单调逼近挡不住——它只知道"计划走 60px"，
不知道机器实际走了 78px。

**k 为什么会被系统性低估**：`aim.fire_sense`（开火时 ×`fire_k_scale 0.85`）与 `aim.ads_sense_by_key`
（按右键切开镜系数）这两组系数是**猜出来**的。若游戏开火/开镜并没有按这个比例降灵敏度，
k 就固定少 17.6% → 每周期都多走一份 → 永远拉过头。这正对上"总是"。

**实测**（`check_overshoot.py`，闭环仿真：检测帧预算 + 1ms 步进跟随线程 + k 误差，框高 300）

| k真/k估 | 当前配置（偏差300） | 当前配置（偏差150） | 不拉过头档（偏差300） |
|---|---|---|---|
| 0.7 | 0px / 4 帧 | 0px / 3 帧 | 0px / 7 帧 |
| 1.0 | 0px / 2 帧 | 0px / 2 帧 | 0px / 6 帧 |
| 1.4 | 1px / 2 帧 | 8px / 2 帧 | 0px / 6 帧 |
| 1.8 | **63px** / 4 帧 | **52px** / 4 帧 | **0px** / 5 帧 |

**新档 `切换-不拉过头.bat`**（`config-不拉过头.json`）：把两道"与 k 无关"的刹车收紧 + 去掉那两组猜测系数

| 键 | 当前 | 不拉过头 |
|---|---|---|
| `aim.step_cap` | 0.75 | **0.35** |
| `aim.abs_move_cap` / `_near` | 0.85 / 0.95 | **0.55 / 0.55** |
| `aim.burst_cap_box_ratio` | 0.75 | **0.30** |
| `aim.near_boost_ratio` | 1.00 | 0.72 |
| `aim.near_damp_ratio` | 0.92 | 0.55 |
| `aim.budget_ratio` / `_initial` | 1.00 / 1.00 | 0.85 / **0.55** |
| `aim.lead_ms` | 50 | **0**（不打提前量＝准星不跑到人身前） |
| `aim.max_step_px` | 520 | 260 |

| `aim.ads_sense_by_key` | true | **false** |

**新增遥测**：`[瞄准] ... 过冲比x.xx`（每 0.35s）。
计算 = 上一周期实测位移 ÷（发出的计数 × k）。`>1.05` = 机器走得比计划远 = k 仍偏小；
`≈1.00` = 标定准确，拉过头应已消失。开关 `aim.overshoot_probe`。

## ★ 2026-10-31 18:45「基准版粉框不乱飘 → 是过滤器把正在锁的人剔掉了 + bat 全是 LF 换行」

指纹：`main.py` **dda390cb08378c51eb40a932bf1d6415**、`config.json` **3fad8c02a9c24bcef5e57fa78fde8c2b**

用户两句关键提示：「打不开而且鼠标依旧乱飞」、「参考基准版，基准版粉框都不乱飘」。查下来是两件事：

**① 真因：过滤器把"正在锁的人"从候选里剔掉，旧框还在被 hold**

基准版（`C:\yolo-trigger-基准-20261026`，main.py md5 7a04237d…、1995 行）**没有**这些过滤器：
`lock_gate` / `team_icon` 绿环 / `ignore_zone` 底部屏蔽 / `person_check`。所以基准里"锁定的那个人"
永远不会从候选消失，粉框自然不飘。而现在只要其中任一过滤器误判（绿环把队友判反、人贴到画面底部
26%、宽高比卡在 0.12/1.6 边缘），`pick_locked` 就会保持旧框 `hold_ms 400ms`——粉框挂在人早就不在
的地方，瞄准点又照这个旧框算，就成了"粉框脱离人体、鼠标跟着飞"。

修法：**锁定框必须有当帧检出支撑**（与通过过滤的候选 IoU ≥ 0.25）。没有支撑只在
`lock.stale_clear_ms`（新增，默认 60ms）内容忍，超时立刻清锁（同时清 `box/t/v`，瞄准一起停），
宁可不锁也不咬空气。实测（`check_lock_support.py`，60fps）：

|---|---|---|

| 人贴画面底部被屏蔽（丢 0.3s） | 24 帧 | **4 帧** |
| 宽高比卡边（丢 0.2s） | 24 帧 | **4 帧** |
| 单帧抖动掉落（丢 1 帧） | 24 帧 | 1 帧（仍容忍，不会一帧就清） |

## ★★ 2026-10-27 22:20「只要人在视野里就锁」—— 全视野分列扫描

### 为什么以前做不到

1. 抓屏区 = 准星 ± `region_size/2`。960 时只看得到准星左右各 480px，游戏画面 2560 宽 → **只覆盖 37%**，两侧 FOV 里的人根本不在画面里。
2. 更隐蔽的一条：代码把 **「准星 = 抓屏区正中心」写死了**（`aim_x = fw/2`）。一旦区域被夹边、或者以后区域跟着目标移动，准星假设就偏了 —— 表现出来是"吸不准/根本没反应"。

### 现在怎么做的

| 机制 | 说明 |
|---|---|
| **水平分列轮转** | 抓屏区沿游戏画面宽切成 `cols` 列（2560 宽 ÷ 1280 = 2 列），**每帧换一列**，两帧扫一遍全场（约 0.06s）。所有列同尺寸 → 推理不变形、shape 恒定 |
| **锁定后固定列** | 一旦咬住目标就停在目标那一列，不再轮转（换列会让跟踪基准跳变）→ 锁定后帧率不变，仍是 26ms/帧 |
| **跨列结果合并** | 各列结果存屏幕坐标（TTL 400ms），合并时转回当前列局部坐标。所以"这一帧在列1、那个目标在列2被看到"照样能拉过去 |
| **准星绝对坐标** | `ScreenCapture.crosshair` 存屏幕绝对坐标，检测段用 `crosshair - region.left` 反算，**不再假设准星在区域中心** |
| **扫描范围 = 游戏画面** | 用 client rect（不是整屏），窗口化时不会去扫桌面 |

### 参数（config.json）

```json
"scan": { "enabled": true, "cols": 0, "side": 0, "ttl_ms": 400, "lock_probe_every": 0 }
```
`cols=0` 自动（= 画面宽 ÷ side），`side=0` 自动（= region_size），`lock_probe_every>0` 表示锁定时也每隔 N 帧偷看一列（防"锁着一个人就当全场没人"）。

`aim.max_dist_px` 900 → **1500**（跨列目标最远偏差 ~1280，旧值会拒绝拉）。

### 实测（`--test --no-window`，游戏窗口 2560×1600 全屏）

```

[扫描] 列 1/2 → 抓屏区 (0, 160, 1280, 1440)（准星在列内 x=1280）
[扫描] 列 2/2 → 抓屏区 (1280, 160, 2560, 1440)（准星在列内 x=0）
[性能] 抓屏 6.0ms | 推理 18.2ms | 逻辑+绘制 0.1ms | 合计 24.2ms
```

坐标自洽性用 `python _check_scan.py` 验证（换列偏差不变、跨列目标可拉、锁定固定列）。

跳帧原理：跟随线程是 1ms 独立线程，不依赖推理帧率 → 跳帧几乎不影响手感。

## 八、已知限制

1. **锁定后覆盖变小**：动态区在 30m 时只有 ±187px（±7.3°），侧翼第二个人暂时看不到；丢锁自动回 1024。
2. **512 推理分辨率是天花板**：想"又广又远"只能导出 imgsz=1024 的引擎（`build_pose_engine.py`，推理约 20~40ms）。
3. **游戏占满 GPU 时自瞄推理变慢**：13ms 是跳帧均摊后的数字，单帧真推理仍约 26ms。
