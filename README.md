## 开火行为（`fire_mode`）
| 模式 | 行为 |
|---|---|
| **`hold`（当前默认）** | **红框出现 → 反应延迟后按住开火键不松 → 目标离开后延迟松开**（持续扫射） |
| `tap` | 每次命中点一发（按下/抬起交替），适合点射 |

`hold` 模式时序：
```
目标进红框 → 随机 110~260ms 反应延迟 → 按住 8 键
目标持续在红框内 → 一直按住
目标离开 / F9 关闭 / 退出程序 → 40~120ms 后松开
另有 6% 概率这次先不按（等 0.25~0.8s 再试）
```

## 热键
| 键 | 作用 |
|---|---|
| `F9` | 开/关自动开火（启动时默认**开**） |
| `F7` | 手动发一次开火键，单独验证"发键通路" |
| `Ctrl+C` / 窗口按 `q` | 退出（退出时自动松开开火键） |

| 参数 | 现在 | 说明 |

## 踩过的坑（都别再踩）
1. **必须管理员权限**：非管理员进程的 `SendInput` 合成按键会被游戏侧拦掉 —— 日志显示"发送成功"但枪不响；管理员启动后正常。
2. **必须放在 `C:\Workzone` 之外**：工作区内的进程会被限制（读不到其他进程内存、截屏可能卡死）。本套是从 `C:\Workzone\压枪宏\三角洲\yolo-trigger` 复制到 `C:\yolo-trigger` 之后才正常工作。
3. **检测窗口会被游戏盖住**：已加 `WND_PROP_TOPMOST` 置顶 + 固定 520×520 左上角、可拖动；再看不见就用 `3-控制台测试.bat`。
4. **torch 必须成对装 CUDA 版**：`torch-2.11.0+cu128` + `torchvision-0.26.0+cu128`，用 `--no-deps`（否则 pip 会把 torch 换回 CPU 版）。来源是阿里 `pytorch-wheels/cu128`；wheel 文件名必须规范（命名成 `torch-cu128.whl` 会被 pip 拒绝）。
5. **ultralytics 8.4 的 `half=` 已弃用**（改用 `quantize`），实测不提速，别加。
6. **异常强杀时按键可能卡住**：任务管理器强杀进程导致开火键一直按着的话，手动按一下那个键即可解除。

## 自瞄控制链（2026-10-25 二轮：修"拉过头"）

坐标链（改错就是"自瞄完全不动"，务必一致）：

```
检测帧(30fps) ── 写 st["tx"],st["ty"] = 目标瞄准点相对屏幕中心的绝对坐标
               └─ 写 st["obs"]      = 该帧实测偏差（用来把航位推算对齐回真实准星位置）
               └─ 写 st["budget"]   = 本周期允许消掉的偏差上限
跟随线程(240Hz) ─ 自己维护 cx,cy = 准星相对屏幕中心的绝对坐标（由发出的鼠标像素累加）
                 每步移动 = (tx-cx) 的一小口 → 与检测帧率解耦、天生不过冲
```

四条防过冲约束：

1. **剩余偏差，不是旧偏差**：旧版整帧只用检测帧那一个偏差 + 大 gain，头 1~2 步就把整段距离花光
   → 准星飞过目标、要等下一帧才拉回来（这就是"拉过头"）。现在每步都用实时的"目标-准星"距离。
2. **单调逼近**：单步步长永远 ≤ 剩余偏差，两轴各自钳位 → 数学上不可能越过目标。
3. **本周期预算按比例分配**（`follow_tau`/`budget_ratio`）：不是"每 5ms 吃固定一口"，否则第一步
   消掉 5% 就撞死区停下、整周期只走 5%，表现为"拉得慢/一顿一顿"。
4. **绝对防过冲闸**（`abs_move_cap`）：本帧累计发出的鼠标像素量不许超过该帧实测偏差。
   即使"像素/计数"系数 k 估歪，也不可能一帧内拉过头。

速度前馈（打提前量）也被"拉过头"坑过，故加三道滤波：
`vel_smooth` 先去抖再求导 → `vel_window_ms`(150ms) 长窗口测速（同样的检测抖动只造成 ~40px/s 误差，
逐帧差分则是 180px/s）→ 速度/加速度限幅 + `lead_step_px` 提前量限速。

## 首答速度与灵敏度自标定（2026-10-25 四改："第一定位不准 / 不能第一时间移动到人身上"）

用户实测反馈：**"不能第一时间移动到人身上，第一定位不准"**。查出三条原因：

**① 硬 bug：`max_dist_px` 500 比检测区域还小**
检测区域是 800×800（中心点模式），它的半对角线 = 800×√2/2 ≈ **565px**。
旧门槛 500px 意味着：敌人出现在检测区四角附近时，自瞄**直接拒绝拉枪**（日志会打
"目标太远，不拉枪"）→ 就是"不能第一时间移动到人身上"。已改 700px。

**② 首答只走 65%，300px 的偏差第一帧还剩 105px**
`budget_ratio` 0.65 是为防过冲设的，但它同样限制了"第一次落到敌人身上"的幅度。
现在新目标出现（或换人，框中心一次跳 >60px）后的 `first_burst_ms`(160ms) 内用
`budget_ratio_initial`(0.95) 一次拉到身上，之后回落到 0.65 保持平稳。
仿真：400px 外首次露面 → 进 8px 用时 **174ms → 106ms**。

**③ 自适应标定公式错了，把系数越学越歪（根因）**
旧公式 `k = (上一帧偏差 - 本帧偏差) / 计数` **没扣掉目标自己的位移**，所以只在
"目标几乎静止"时才敢学；实战里敌人一直在动 → 几乎学不到，或者学歪：

| 真实灵敏度 | 旧公式学到的 k | 新公式学到的 k |
|---|---|---|
| 1.0 | **0.60**（反而变差） | 1.00 ✅ |
| 0.5 | **0.35** | 0.51 ✅ |
| 2.0 | **1.03** | 1.89 ✅ |

新公式用物理关系直接解：偏差 `e = 目标 - 准星` → `Δe = 目标位移 - k×计数`
→ **`k = (目标位移 - Δe) / 计数`**，目标在跑也能标定，样本少时学习率大（先快后稳）。
见 `update_aim_k()`（模块级函数，单测 `_test_k_calib.py`）。

### 闭环稳定性护栏（2026-10-25 加）

| 护栏 | 作用 |
|---|---|
| 未标定前不许用大预算 | `aim_k_samples < 2` 时首答预算压到 0.5 —— 避免 k 未知时增益 >1 发散 |
| 过冲抑制 | 偏差符号相对上一帧翻转（刚冲过目标）→ 0.25s 内预算压到 0.45 |
| 标定只在动作够大时直采 | 首个样本要求预计移动 ≥50px 且计数 ≥12，结果限制在 0.4~3.0 |
| ΔB 只能从"没发移动的帧"估 | 画面里的位移已含我们自己的移动，直接当 ΔB 会让 k 越学越小 |

## 开火延迟与跟枪（2026-10-25 六改："开火延迟太高 + 跟枪跟不上"）

### 开火延迟的构成（先看清链条，别乱调）

```
目标进命中圈(检测帧) → hold_arm_at = now + reaction_delay_ms
                    → 同帧或下一帧判定 now >= hold_arm_at → key_event 按下
```

关键：`reaction_delay_ms = 0` 时**同帧就会按下**（`now >= now` 成立），不用等下一帧。
旧值 `[18,45]` 意味着至少再等一帧检测，实测 40~78ms；现在 `[0,6]`，实测：

```
[按住] 8 按住开火（目标距准星 41px 高 279px | 进圈→按住 8ms）
[按住] 8 按住开火（目标距准星 41px 高 279px | 进圈→按住 7ms）
```

**7~8ms 已是软件层下限**，剩下的硬下限是检测帧率：44fps → 命中判定 22~33ms 才更新一次。
日志里新增的 `进圈→按住 XXms` 就是量这个的。以后判断"开火慢"先看它：小于 40ms 说明
软件侧没拖后腿，该去提帧率（换更小的 pose engine），别再去改 reaction。

同时放开：`trigger_radius_px` 30→**40**、`fire_hysteresis_ms` 120→**60**、`skip_chance` 0.01→**0**。

## 性能第二轮（2026-10-25 七改）：真正拖慢它的是「GPU 被游戏占满」

### 实测证据（`python bench_pose.py` / `python cmp_engines.py`）

| 状态 | 512 engine 推理 | 说明 |
|---|---|---|
| GPU 空闲 | **4.14ms** | 老基线，44fps 那组数字 |
| 三角洲在跑（GPU 87~93%） | **15~19ms** | 同一份代码，劣化近 4 倍 |
| 同上，换 **416** engine | 18.6ms | 只省 0.8ms —— **缩尺寸没用** |
| 同上，开高优先级 CUDA 流 | 19.8ms | 也没用（WDDM 跨进程抢占，CUDA 内部优先级管不着） |

结论：**满载时的瓶颈是 GPU 排队，不是算力**。所以"开火延迟高 / 跟枪跟不上"在游戏开着的时候
八成是这个原因，而不是控制参数。看 `nvidia-smi --query-gpu=utilization.gpu` 一眼就清楚。

### 本轮落到代码里的（都是 CPU 侧确定收益）

| 改动 | 收益 |
|---|---|
| letterbox 画布复用（不再每帧 `np.full` 786KB） | **0.814ms → 0.540ms**，省 0.27ms/帧（34%） |
| 后处理不再整块 `.float()` 300K 元素，直接 fp16 比较 | 省一次 fp16→fp32 GPU 转换 |
| 前处理只做一次精度转换（原 `.float()` + `.half()` 两次） | 省一个中间张量 |
| 同步改成本 CUDA 流同步（`_cs.synchronize()`） | 少等别的流 |
| 高优先级 CUDA 流（`POSE_HIGH_PRIORITY=0` 可关） | 实测无收益，保留无害 |
| `6-实战-无窗口.bat` 启动后自动把 python 提到 High 优先级 | 帧间隔更稳 |
| 新增 `yolo11n_pose_416_fp16.engine`（28.1MB） | 空闲时比 512 快约 2ms，满载仅 0.8ms |

想用 416：把 `config.json` 的 `pose_engine` 改成 `yolo11n_pose_416_fp16.engine`、`imgsz` 改 416。
代价是远距离小目标略差。默认仍是 512。

### 想让帧率真回到 44fps 以上，只能处理 GPU 争抢

2. 关 NVIDIA Overlay、MCE HUB 的动画/叠加层、浏览器的"硬件加速"；
3. 用 `cmp_engines.py` 在**游戏开着**的状态下复测，才是有意义的数字。
## 第八轮（2026-10-25 晚）：开镜视角异常移动 + 框跟不上 + 插桩修复

按"先测量再改"的规矩，先各建一个能量化的回路，把症状变成一个数。

### 一、开镜视角异常移动 —— 根因是"视野缩放被当成了准星偏离"

| 环节 | 事实 |
|---|---|
| 换人判定（旧） | `\|框中心跳变\| > 60px` 就算"新目标" → 触发首答脉冲（预算 1.0 + 标定清零） |
| 开镜做了什么 | 视野以准星为中心放大 z 倍：目标相对准星的**偏移**放大 z 倍，框高也放大 z 倍 |
| 量化结果（`_test_ads.py`） | 4x 镜、真实动画（8 帧 1→4 倍）、目标偏移 400px：**17 帧里 16 帧被判成换人** |
| 后果 | 整个开镜动画期间每帧都在发首答脉冲 → 满预算猛拽 → 一开镜视角就被拽走 |

**物理本质**：开镜时"像素偏差变大"不等于"准星偏了"。人是瞄着的，变的是画面几何。
把放大后的像素偏差当误差去拉枪，就是凭空制造一次错误修正。

**改法（三条，都在 `main.py`）**：

1. `is_new_target()`：换人判定改成**尺度补偿**——
   以准星为缩放中心，先把上一帧的框按"框高比"缩放，再算残差 ÷ 框高。
   纯缩放时残差≈0；真换人时很大。→ 误判 16/17 → **1/17**（只剩第一帧，本该如此）。
2. **视野缩放稳定期**：同一目标的框高两帧变化 >10% ⇒ 认为视野在缩放，
   进 `fov_settle_ms=220ms` 稳定期，期间预算压到 `0.15`、单帧限幅 `50px`。
   稳定期一过立刻恢复，所以不牺牲"够快"。
3. **腰射/开镜两套灵敏度系数** `k`：游戏里开镜灵敏度 ≠ 腰射，一套 k 混用会让闭环增益失准
   （增益>1 就是"冲过去再拉回来"）。现在 `aim.adaptive` 标定分别写进两套值。

另外把甩动量级降下来（`_test_jump.py` 已证「单周期峰值 = max_step_px」）：

| 参数 | 改前 | 改后 | 单周期峰值 |
|---|---|---|---|
| `max_step_px` | 220 | **120** | 220px → 120px |
| `budget_ratio_initial` | 1.00 | **0.85** | — |
| `jump_cap_px` | 120 | **90** | — |
| 缩放稳定期内 | — | 比例 0.15 / 限幅 50 | **50px** |

### 三、⚠️ 插桩 bug（这条比上面都重要）

原来 `[性能]` 里"推理"那一项，实际统计的是 **推理 + 全部自瞄/开火逻辑 + 绘制**：

```
_pt_c = perf_counter()   # 推理结束
...自瞄/开火/绘制...
_pt_c = perf_counter()   # ← 覆盖了推理结束时刻
perf_acc[1] += _pt_c - _pt_b    # 标签"推理"，含绘制
perf_acc[2] += _pt_c2 - _pt_c   # 标签"绘制"，恒 ≈0
```

所以以前日志里"其他/绘制 0.0ms"永远是假的，"推理"数值偏大。
**这一轮之前的"推理 Xms"读数都该打折扣看。** 现已改成三段独立计时。

修好后立刻看见真相（游戏关闭、GPU 空闲）：

| 模式 | 抓屏 | 推理 | 逻辑+绘制 | 合计 |
|---|---|---|---|---|
| 无窗口 | 2.0ms | 6.0ms | 0.0ms | **8.0ms（65fps）** |
| 有窗口 | 1.2ms | 6.7ms | **0.7ms** | **8.6ms（115fps）** |

（有窗口反而 fps 更高，是因为 fps 只统计"每轮"——窗口模式下抓屏线程有更长的时间攒帧。）

### 五、裁剪精算（`crop_track`）：精度收益确定，速度收益拿不到

  框中心偏差 **2.6px**、框高偏差 **2%**（`_test_crop_agree.py`）。
- **速度**：想靠 256 小图提 5 倍（实测 62.3ms → 12.5ms）**做不到**——
  需要第二个 engine，而 8GB 显存被游戏占了 6.6GB，再加载一个后推理反而恶化到 106~141ms。
  复用主 backend（同一套引擎吃小图）则显存零成本，但输入尺寸不变 ⇒ 速度不变。

  头部关键点更锐利。这是"锁头更准"的收益，不是"更快"。
- 安全闸：目标框高 > `crop_side × 0.95` 时回全图（否则框会被窗口截断——实测 256 窗口
  装 463px 高的近距离目标，框高偏差 45%）。

## 移动不平滑 / 打头胸旁边的空气（2026-10-26 修复）

用户报两条：**① 移动不平滑；② 瞄准不到头胸，打在头胸旁边的空气上**。
离线把两条都量化后，各找到一处确定缺陷（都改在 `main.py`，配置加了 5 个参数）。

### ① 不平滑 = 亚计数被整块丢掉（跟随线程死锁）

旧代码在把像素换算成鼠标计数后有一句：

```python
if abs(mx) < 1.0 and abs(my) < 1.0:
    continue        # 不足 1 计数，等误差长大再说
```

问题出在**两次不该丢的取整**：

1. `if abs(mx) < 1: continue` —— 只要这一小步凑不满整数计数就整块丢掉，**残量不记账**。
2. 取整后的 `_ix` 用来发鼠标，但"单调逼近：不许越过目标"的钳位、
   航位推算、预算记账**全都还在用未取整的 `mx`** —— 发出的位移和记的账不是一个数。

实测（`_test_aim_chain.py` C 项，伺服 200ms/步 = 每周期只走一步、无噪声）：
偏差 5px 时每步算出约 0.68 计数：

| | 60 周期发出的步数 | 单步实际位移 | 末残差 |
|---|---|---|---|
| 旧 | **1 步**（一步到位后残量再不记账） | 4px（取整放大） | 1.00px |
| 新 | 逐步补齐（残量累加） | 1px 一级 | 1.00px |

关键差别是**中间过程**：旧代码靠"取整放大"一步跳过去（偏差小时每步都被放大到 1 计数，
位移量随误差变化不连续），新代码按亚计数逐步补 —— 这就是"一顿一顿"和"平滑"的区别。
在亚计数与整数之间来回切换的区间（剩余偏差 1px ~ 死区），旧代码只有"跳 1 计数"和"完全不动"两种状态。

后果有两个，正好对应用户的两句反馈：
- 趋近阶段：零碎的 0.5~1 计数位移被反复丢弃/错记 → 准星走一步停一下，**一顿一顿、贴不上**；
- 急反向（横移变向）时：记账与实际发出的位移不符 → 实测折返跑过冲 **17.96px**（旧）→ **5.89px**（新）。

修法：
- 残量 `_carry_x/_carry_y` **累加**（`+= mx - 已发出的整数计数`），下一步优先补齐，
  亚计数不再丢失；残量钳 ±0.75 计数防止 k 估歪时抽搐。
- 单调钳位、航位推算、预算记账全部改用**实际发出的整数位移**（`_ix*kx`），
  与桌面真实位移一致（原来用未取整量，记账与实际不符）。

### ② 打空气 = 关键点猜飞了也照瞄

`pick_pose_point` 原来只用**置信度**筛关键点。远景/背身/遮挡时模型经常把鼻子、肩膀
猜到框外，只要 conf 过线就照样当瞄准点 → 准星贴着人但不在身上。

修法：加**几何合理性闸**，用锁定框（这一帧最可信的几何先验）卡候选点：

| 参数 | 默认 | 含义 |
|---|---|---|
| `head_y_max` | 0.45 | 头必须在框高 0~45% 之间（框外/太高 → 该部位本帧不可用） |
| `chest_y_min` / `chest_y_max` | 0.12 / 0.70 | 胸必须落在框高 12%~70% 之间 |
| 横向（写死） | ±12% | 允许肩比框宽，跑出这个余量就是猜飞 |
| `pose_jump_cap_px` | 45 | 瞄准点单帧位移上限（换部位/瞬间猜飞时不给准星抽一下） |

任一部位不合格就**换部位**（胸不可用→用头）；全都不合格就**退回按框高比例瞄**
（`aim_height_ratio=0.2`，稳定落在人身上）。因为几何闸兜住了瞎猜点，`pose_conf`
可以放心从 0.6 调回 **0.4**（原来提到 0.6 是为了挡瞎猜点，代价是远景容易一个部位都拿不到）。

另外：**换人时清空部位粘滞、瞄准点平滑、速度估计与提前量** ——
否则新目标头几帧在按旧目标的关键点位置做 EMA，首答带一段旧目标滞后。

### 一个教训（别再踩）

**夹具/探针的坐标符号必须和被测代码逐字核对**。这次排查中我一度把
"准星绝对坐标 = 目标 − 观测偏差" 误判成符号反了，改成 `+` 后闭环立刻发散
（准星每周期朝反方向跑 124px）。真实关系是：检测帧写进 `st["obs"]` 的
`ex = tx - aim_x`，即**"准星还要走多少才到瞄准点"**，所以 `cx = tx - obs` 是**对的**。
自检办法：把抓屏帧里的目标放在**帧中心左侧**（框中心 x < 400），
正确行为是准星往左走（计数累加为负）。

### "慢了"的复查（2026-10-27）：控制器没变慢，快的是旧代码的取整放大

用户反馈"慢了"后，用四组独立对照复核：

| 判据 | 旧 | 新 |
